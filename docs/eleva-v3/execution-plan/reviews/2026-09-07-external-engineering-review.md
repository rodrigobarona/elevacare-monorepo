My thought process
Eleva.care v3 Execution Plan
Engineering Evaluation and Recommended Amendments

Prepared: 7 September 2026
Review status: Conditional approval
Audience: Engineering, product, design, security, finance, compliance, and operations
Source reviewed: Eleva.care v3 execution-plan HTML and the current public Eleva.care website

1. Executive summary

The Eleva.care v3 plan is unusually comprehensive. It covers the complete platform lifecycle:

identity and authorization;
public marketplace and booking;
expert offer management;
member and clinic applications;
payments, payouts, refunds, and disputes;
Portuguese invoicing;
transactional notifications;
video sessions;
encrypted clinical records and AI-assisted reports;
administration and operations;
observability, security, migration, and launch.

The overall architecture is coherent and appropriate for an API-first, multi-tenant healthcare marketplace. The strongest parts are:

Clear package ownership of vendor SDKs.
Explicit tenant isolation and audit requirements.
A transactional-outbox direction for external side effects.
A detailed booking and payment state machine.
Separating platform-fee invoices from expert service invoices.
Human-reviewed AI output and explicit PHI controls.
Migration rehearsals and guarded production operations.
Strong attention to UX, localization, empty states, and accessibility.

However, the plan should not yet be accepted as a committed delivery schedule or implemented unchanged. Several technical contradictions and sequencing gaps could create payment, booking, security, or migration failures.

Overall recommendation

Approve the product and architectural direction, but condition implementation on resolving the critical findings in this review.

It is reasonable to begin Phase 0, Phase 1, and a set of technical spikes. It is not yet advisable to commit to the current phase estimates or proceed directly into the payment, recording, or migration implementations.

2. Scope and limitations of this review

This is a design and execution-plan review. It is based on:

the supplied generated HTML;
the architecture and requirements described in that document;
the visible public Eleva.care website;
relevant public vendor documentation.

This review did not include:

direct access to the monorepo;
validation of the claimed “roughly 40% built” state;
execution of tests or migrations;
review of production infrastructure;
validation of existing database schemas;
validation of contracts, BAAs, DPAs, tax advice, or legal opinions;
testing against Stripe, Daily, Better Auth, TOConline, Neon, Resend, Twilio, or WorkOS accounts.

All estimates must therefore be revalidated after a repository audit.

4. What the plan gets right
   4.1 API-first and agentic-first structure

The plan consistently requires:

HTTP route handlers in apps/api;
explicit authentication models;
JSON and OpenAPI contracts;
typed API clients;
API-key, bearer-token, and JWT support;
thin Server Actions;
Zod validation.

This is a good foundation for browser applications, future mobile applications, internal automation, and agentic clients.

The definition of done should retain:

OpenAPI updates for every endpoint change;
client regeneration or typed client changes in the same PR;
explicit route auth and rate-limit classification;
no direct domain mutations hidden inside UI applications.
4.2 Vendor ownership boundaries

The proposed package boundaries are excellent:

Better Auth only in @eleva/auth;
Stripe only in @eleva/billing;
Daily only in @eleva/video;
TOConline and Moloni only in @eleva/accounting;
Resend and Twilio only in @eleva/notifications;
Blob access only through @eleva/storage;
AI Gateway calls only through @eleva/ai.

These boundaries reduce vendor lock-in, improve testing, and make it possible to enforce security and compliance centrally.

They should be supported by:

ESLint boundary tests;
a documented package dependency graph;
CI tests containing deliberate invalid-import fixtures;
prevention of circular dependencies between domain packages.
4.3 Audit and tenant isolation

The plan repeatedly requires:

org_id on tenant data;
RLS policies;
withOrgContext;
isolation tests;
withAudit around mutations;
a separate audit database.

That is appropriate for the domain. The key requirement is that the audit write and domain mutation be connected through a durable outbox in the same primary-database transaction. A direct write to a second database cannot be atomically committed with the primary mutation.

4.4 Offer and scheduling model

The model separating:

event type—the service;
delivery mode—how and where it is delivered;
schedule—when it is delivered;
location—where an in-person session occurs;
booking link—private override and capability;

is significantly better than a single session_mode field.

It supports real expert practices involving:

multiple locations;
different prices per location;
language restrictions;
country restrictions;
different availability for video, phone, and in-person work;
private or invite-only scheduling.
4.5 Payment intent and booking identity design

The proposed ordering for payment creation is strong:

Create a durable pending booking and payment-ledger row.
Commit the transaction.
Call Stripe using a stable idempotency key.
Persist the resulting PaymentIntent in a second transaction.
Reconcile timeouts and partial failures.

This avoids calling Stripe inside a database transaction and gives every external payment a durable local owner.

The reservation capability token is also a strong design:

random token returned once;
only its hash persisted;
not placed in a URL;
signed-in reservations bound to the user;
unauthorized lookup returns 404 rather than confirming existence.
4.6 Two-tier invoicing

The plan correctly recognizes two different commercial relationships:

Eleva → expert: invoice for Eleva’s platform fee.
Expert → member: invoice for the professional service.

This distinction must remain explicit in code, accounting, reporting, refunds, and reconciliation.

4.7 AI and PHI posture

The AI design correctly requires:

AI Gateway ownership inside @eleva/ai;
approved-model allow-lists;
zero-retention enforcement for PHI-bearing requests;
structured output validation;
encryption of transcripts and drafts;
no automatic publication;
expert review before publication;
no content in logs.

That is the right baseline. Zero retention alone, however, is not sufficient for healthcare compliance; contractual and regional-processing requirements are addressed later in this review.

4.8 Launch and migration discipline

The plan includes several safeguards that should be preserved:

dry-run by default;
explicit production flags;
typed project confirmation;
migration checksums;
idempotent mapping;
rehearsals;
operator approval before production mutation;
a seven-day launch watch;
delayed decommissioning.

These are all valuable.

5. Critical findings to resolve before feature implementation
   P0-1: Stripe refund logic does not match separate charges and transfers

The plan correctly selects separate charges and transfers:

charge on the platform;
no transfer_data;
no Stripe application fee object;
transfer expert funds later.

However, Phase 6 says a refund should use reverse_transfer: true. With separate charges and transfers, refunds and transfers are separate operations:

Refund the platform charge.
If funds were already transferred, create an explicit transfer reversal.
Handle reversal failure, partial reversal, and insufficient connected-account balance.

This is not the same as a destination-charge refund.

Required correction

Replace the refund contract with:

stripe.refunds.create({ payment_intent, amount });
locate the associated transfer from payout_states.stripe_transfer_id;
call the transfer reversals API separately;
persist refund and reversal as separate state transitions;
support partial refunds and proportional transfer reversal;
reconcile when the refund succeeds but the reversal fails;
issue the fiscal credit note based on the completed refund policy;
never mint a new transfer idempotency key merely because a previous response was lost.

Stripe reference:
https://docs.stripe.com/connect/separate-charges-and-transfers

P0-2: Redis locking is not sufficient to guarantee one booking per slot

The plan tests 100 concurrent reservations and expects one winner. A Redis lock helps, but it is not the final consistency boundary.

Duplicate bookings can still occur if:

the lock expires during a slow transaction;
Redis fails over;
two processes disagree about lock ownership;
a stale worker commits after losing the lock;
the database and Redis operations partially fail.
Required correction

Add a PostgreSQL-level constraint as the final source of truth.

Recommended options:

a GiST exclusion constraint over the expert and a tstzrange;
or a normalized slot key with a unique partial index;
or a serializable/advisory-lock transaction plus a conflict constraint.

The constraint must cover active reservations and confirmed bookings according to the exact overlap rules. Redis can remain a performance optimization.

P0-3: Cross-subdomain session cookies require a complete CSRF and subdomain threat model

The plan proposes a Better Auth session cookie on .eleva.care. This enables SSO across applications but increases risk:

any compromised subdomain may influence parent-domain cookies;
credentialed cross-origin requests require careful CORS handling;
cookie-authenticated mutations need CSRF protection;
abandoned DNS records can become a session-security issue.

Bot protection and rate limiting do not replace CSRF protection.

Required correction

Before Phase 2, document and test:

a complete inventory of every \*.eleva.care subdomain;
prevention and monitoring of subdomain takeover;
Secure, HttpOnly, and appropriate SameSite behavior;
a secure cookie prefix compatible with a parent-domain cookie;
strict trusted-origin and CORS allow-lists;
Origin/Referer validation for cookie-authenticated mutations;
CSRF token or custom-header protection where required;
no wildcard credentialed CORS;
secret and cookie rotation;
preview-deployment behavior;
logout and session revocation across all applications.
P0-4: Consent collection is sequenced after the booking flow that needs it

Phase 4 collects:

terms consent;
privacy consent;
health-data-processing consent.

Phase 5 creates the consents table.

A production booking cannot rely on UI checkboxes without a durable, versioned record of what was accepted.

Required correction

Move the minimum consent schema into Phase 4:

consent kind;
legal-text version;
timestamp;
source;
locale;
booking or reservation reference;
guest email or user ID;
IP/user-agent policy if legally approved.

Phase 5 can then add the member management UI and withdrawal flows.

P0-5: public_handles is introduced too late

Phase 4B says expert onboarding uses public_handles, but Phase 11 creates the table.

This creates an impossible dependency.

Required correction

Move public_handles to Phase 4 or Phase 4B. It should own the namespace before expert handles are created. Phase 11 should extend the existing table with clinic owners rather than introduce it.

P0-6: Multi-currency behavior conflicts with the Portugal launch and with the prompt

Most of Phase 4 correctly says the PaymentIntent currency comes from the reservation snapshot. A later section hardcodes currency EUR.

The broader plan also suggests that offers may use any currency supported by the expert’s Connect account. That introduces:

FX and settlement questions;
VAT and invoice-currency handling;
rounding;
refund exchange-rate differences;
reconciliation complexity;
display and pricing rules.
Required correction

For Portugal launch, choose one of these explicitly:

Recommended: EUR-only at launch.
Support multiple presentment currencies with a separate approved accounting design.

Do not leave both contracts in the plan.

P0-7: Daily HIPAA recording conflicts with the proposed storage workflow

The plan later enables Daily cloud recording and downloads it after transcription. Daily’s HIPAA restrictions generally require customer-managed recording storage rather than Daily’s default cloud storage.

Required correction

Before Phase 10, confirm and document:

signed Daily BAA;
Healthcare/HIPAA account mode;
supported recording type;
customer-managed storage requirement;
exact EU bucket and region;
encryption and retention;
transcript-processing region;
webhook payload sensitivity;
recording-deletion guarantees;
behavior when consent is withdrawn;
whether Daily transcription is enabled under the agreed terms.

If the required compliant storage is not available, keep recording and transcription disabled.

Daily reference:
https://docs.daily.co/guides/privacy-and-security/hipaa

P0-8: sessions.eleva.care has conflicting DNS ownership

Phase 9 assigns sessions.eleva.care as Daily’s branded custom domain. Phase 15 says to move the sessions domain to a Vercel project.

Both cannot own the same hostname.

Required correction

Choose one:

sessions.eleva.care is a Daily custom domain and remains mapped according to Daily’s DNS requirements; or
the join application uses sessions.eleva.care, while Daily receives a different subdomain such as video.eleva.care.

Document the final routing and CSP model.

P0-9: The rollback design is effectively a second migration platform

Phase 14 proposes reconstructing every post-cutover mutation and replaying it back into the MVP, including:

identities;
bookings;
updates and deletes;
payments and payouts;
records;
CRM;
notifications;
data with no MVP equivalent.

This is not a conventional rollback. It is a bidirectional synchronization system and could be as complex as the migration itself.

Required correction

Adopt a narrower cutover model:

Freeze MVP writes.
Run the final idempotent migration.
Switch infrastructure while v3 write paths remain restricted.
Complete smoke tests.
Open v3 writes only after the acceptance point.
Before the acceptance point, rollback is DNS/configuration only.
After accepting v3 writes, use forward recovery unless a deliberately engineered dual-write/CDC system exists.

For payment safety, retain a dedicated Stripe-source-of-truth reconciliation procedure. Do not claim that all new v3 product data can safely be replayed into the MVP unless that system has been designed and independently tested.

P0-10: External APIs must not be called while holding database transactions

The plan correctly avoids this for PaymentIntent creation, but Phase 10 proposes:

locking a session row;
calling Daily;
then updating the database within the same transaction.

This can hold database locks across slow network calls and still cannot atomically commit the Daily and database changes.

Required correction

Use a desired-state state machine:

Commit desired recording state and increment a version.
Publish a durable job.
The worker calls Daily outside a database transaction.
Update the applied version with compare-and-set semantics.
Re-read desired state; run again if it changed.
Reconcile periodically.

Use the same pattern for other external systems when strict synchronization is required.

6. Important P1 findings
   6.1 The “one phase, one PR” model is incompatible with the actual scope

Several phases include:

schema migrations;
APIs;
SDK integration;
multiple frontends;
localization;
E2E tests;
infrastructure;
documentation.

Even the predefined two-PR splits are too large in many cases.

Recommendation

Treat each phase as an epic with a completion gate, not as a single PR.

Each phase should contain a predefined sequence of small, mergeable PRs, for example:

schema and migrations;
domain package;
API contract and client;
UI;
workflow and external integration;
E2E and documentation.

Every PR should leave main buildable and ideally deployable behind a flag.

File and line limits are useful review heuristics, but semantic and rollback boundaries matter more than raw size.

6.2 Security cannot wait until Phase 13

Phase 13 introduces:

route-guard coverage checks;
complete security headers;
Sentry configuration;
dependency auditing;
analytics consent;
full observability.

Some of these controls are needed earlier.

Move earlier

Phase 1–2:

secret scanning;
dependency audit and exception policy;
baseline Sentry and structured logs;
correlation IDs;
CSP baseline;
secure-cookie tests;
route auth/rate-limit declarations.

Phase 4:

BotID and route-guard coverage checks;
payment and booking dashboards;
availability and payment synthetic checks.

Phase 6–8:

financial and notification reconciliation alerts.

Phase 13 should verify and harden existing controls rather than introduce the first production-grade implementation.

6.3 The outbox needs per-subscriber delivery state

The plan evolves the outbox from one subscriber to many:

guest activation;
notification delivery;
video room creation;
CRM updates;
invoice events;
structured logging.

A single published_at field does not identify which subscribers succeeded.

Recommendation

Add:

text
domain_event_deliveries

- event_id
- subscriber_id
- status
- attempts
- claimed_at
- completed_at
- last_error
- unique(event_id, subscriber_id)

Mark the event complete only after every required subscriber reaches a terminal successful state.

6.4 Resend does not provide unlimited exactly-once delivery

The plan describes email as exactly once through Resend idempotency keys. Resend documents a finite idempotency window, currently 24 hours.

Recommendation

Use this language:

Email delivery is effectively once within the provider idempotency window and reconciled through Eleva’s durable delivery ledger outside that window.

Retain the durable claim-before-send mechanism and persist the provider ID.

Resend reference:
https://resend.com/docs/api-reference/idempotency

6.5 Booking confirmation status codes conflict

One section says:

first confirmation: 201;
idempotent retry: 200.

A test later expects 200/200.

Recommendation

Standardize:

first successful public confirmation: 201;
retry for an already confirmed booking: 200;
webhook handler returns its normal webhook acknowledgment independently.
6.6 Async payment methods need an explicit reservation policy

Dynamic Payment Methods can expose methods that are not immediately final. A five-minute reservation may expire while a payment is still processing.

Recommendation

Classify payment methods:

synchronous methods allowed under the five-minute hold;
asynchronous methods that extend the hold;
methods excluded from launch.

The expiry worker must not cancel an intent that can still legitimately succeed without a compensating state machine.

6.7 Connect capability requirements may be excessive

The plan requires charges_enabled, payouts_enabled, and Stripe Identity verification before publishing. With separate charges and transfers, the platform charges the member. The connected account primarily needs to receive transfers.

Requiring card-payment capability and separate Stripe Identity verification may duplicate Connect KYC and increase onboarding abandonment.

Recommendation

Confirm with Stripe and legal counsel:

required capability for transfer recipients;
whether card_payments is needed;
whether charges_enabled is relevant;
whether Stripe Identity is legally or operationally necessary;
whether Connect’s own verification is sufficient.
6.8 Fee, VAT, and expert-net economics are not fully defined

If Eleva retains 15% and issues an invoice with 23% VAT, the plan must define whether:

the 15% includes VAT;
VAT is added on top;
the expert receives gross minus fee, gross minus fee-plus-VAT, or another amount;
Stripe processing fees are borne by Eleva or the expert;
clinic bookings at 0% commission transfer the full amount and leave Eleva to absorb payment fees.
Recommendation

The accountant-approved matrix must define:

text
booking gross
platform fee net
VAT on platform fee
platform fee gross
payment processing fee
expert transfer amount
credit-note allocation
rounding rule
currency

This should become the only financial calculation contract.

6.9 Historical invoicing is not addressed

Migrated paid bookings will not naturally replay payment_intent.succeeded. The plan must decide whether historical payments:

already have valid invoices;
need imported invoice references;
require lawful backfill;
must be excluded from v3 invoice generation.

This requires accountant approval before migration.

7.2 Database and RLS

The use of RLS is appropriate, but some resources have more complex visibility than one active organization:

a booking is visible to expert and buyer organizations;
a record is controlled by an expert organization but sometimes visible to one member;
session participants have direct user-level access;
staff-only webhook tables have no tenant organization.
Recommendation

Define named policy classes:

tenant-owned;
dual-organization;
owner-user-visible;
published-to-member;
participant-visible;
staff-only;
public-read;
service-only.

Every table migration should declare its class and use a standard test suite. Do not force all visibility through a single generic org_id policy.

7.3 Scheduling and booking

The offer model is strong. The main missing safeguards are:

database-level overlap prevention;
fencing for expired Redis locks;
explicit handling of asynchronous payment methods;
durable guest consent records;
explicit booking-link use-release idempotency.

Availability must use one canonical time model:

store timestamps in UTC;
store schedule-local times with an IANA timezone;
convert only at boundaries;
test DST gaps and folds;
never infer timezone from numeric UTC offset alone.
7.4 Payments and payouts

The separate-charges-and-transfers choice supports delayed payouts and approval requirements. It is appropriate if Eleva accepts platform-balance liability.

Before implementation, finance and engineering must jointly approve:

who pays processing fees;
reserve policy;
negative-balance recovery;
partial refunds;
transfer reversals;
disputes after payout;
multi-currency policy;
clinic payout destination;
first-payout review;
payout threshold;
tax calculation.

Stripe webhook configuration must include connected-account events when relying on events such as connected-account payouts.

7.5 Portuguese invoicing

The two-tier design is valid, but it cannot be treated as a purely technical integration.

Before Tier 1 implementation, obtain written approval for:

invoice timing;
fee VAT basis;
reverse-charge conditions;
VIES failure behavior;
customer address and NIF requirements;
credit-note timing;
rounding;
payment/refund relationship;
historical transactions;
test-series procedure;
document finalization and AT communication.

TOConline hostnames and OAuth behavior should be configurable and confirmed against current official documentation rather than hardcoded from historical implementation notes.

TOConline documentation:
https://api-docs.toconline.pt

7.6 Notifications

The delivery-ledger approach is good. Required improvements:

use per-subscriber outbox state;
describe email guarantees accurately;
retain at-least-once semantics for SMS;
protect Twilio callbacks using regional credentials and exact public URL reconstruction;
avoid specialty, diagnosis, report content, or sensitive session context in subjects and SMS;

prevent auth-package/notifications-package circular dependencies.

https://www.twilio.com/docs/global-infrastructure/understanding-regions

7.7 Daily video

Daily is a reasonable fit if the Healthcare agreement and regional requirements are confirmed.

Before Phase 9:

validate room-creation reconciliation against the actual Daily API;
confirm whether custom metadata can be stored and searched as proposed;
confirm webhook-signature details;
verify ejection and ban APIs;
use UUID participant IDs;
decide whether chat is appropriate for clinical sessions;

confirm customer-managed EU storage;
confirm transcription processing;

7.8 Records, encryption, and AI

The envelope-encryption direction is defensible, but it requires additional controls:

KEKs must differ by environment.
KEKs need offline escrow and tested recovery.
AAD should be mandatory for PHI and bind ciphertext to organization, table, row, field, and version.
Backup retention must be considered when claiming crypto-shred.
Deleting a live DEK does not automatically erase copies in database backups.
Key rotation must be tested under concurrent reads and writes.
Audit payloads must never contain decrypted content.

The proposed Decrypted<T> redaction wrapper is helpful but not sufficient. Plaintext can still leak through:

destructuring;
interpolation;
exception messages;
response DTOs;
custom logger fields.

Preventive boundaries and object-level redaction tests are still necessary.

For AI:

zero retention must be enforced per request;
underlying providers must be contractually approved;
BAAs/DPAs and processing regions must be confirmed;
model routing must fail closed;
clinical output must remain a draft;
evaluation and incident procedures must exist.

Vercel AI Gateway ZDR reference:
https://vercel.com/docs/ai-gateway/security-and-compliance/zero-data-retention

7.9 Clinic SaaS

The clinic organization model is coherent. Key questions remain:

If clinic bookings have 0% commission, who pays payment processing fees?
Is payout routed to the clinic or expert, and when is that choice frozen?
Does the clinic need Connect charge capability or only transfer capability?
What happens to booked sessions when an expert leaves the clinic?
Who owns and retains clinical records created in a clinic context?
Can clinic administrators see clinical notes, or only operational metadata?

Clinical-record access must be explicitly separated from clinic billing and scheduling roles.

7.10 Admin console

The planned role separation is good. High-risk operations should add:

recent MFA or passkey step-up;
no money action while impersonating;
no staff-on-staff impersonation;
dual control for large payout overrides;
actor and approver separation;
mandatory reason;
immutable audit record;
session age limit;
notifications for high-risk actions.

CodeRabbit and one general human approval are not substitutes for a finance approver or security approver.

14.1 Replace “phase equals PR”

Use:

Phase: business or architectural outcome.
Workstream: independently owned part of the phase.
PR: small deployable change.
Release gate: evidence that the phase outcome is complete.
14.2 Use expand-and-contract migrations

For high-risk migrations:

Add new schema.
Dual-read or backfill.
Validate.
Switch writers.
Observe.
Remove old schema in a later PR.

Avoid dropping identity tables and changing all consumers in one step unless the repository audit proves it is safe.

14.3 Introduce environment mutation rules before Phase 15

Production already requires explicit approval. Apply a lighter version to staging:

commands must state the target environment;
destructive operations require confirmation;
IDs and evidence are recorded;
no agent may mutate external infrastructure using ambiguous credentials;
scripts must fail closed when environment identity is unavailable.
14.4 Treat AI review as advisory

CodeRabbit is useful, but it is not a substitute for:

domain-owner review;
security review;
finance approval;
privacy approval;
migration approval;
production operator approval.

Date-specific rate limits and CLI behavior should live in a tooling note, not in the permanent architectural SSOT.

The Eleva.care v3 plan is a strong architectural blueprint and demonstrates serious consideration of payments, privacy, tenant isolation, invoicing, migration, and operational readiness.

It makes sense as a target-state and program plan.

It does not yet make sense as a literal, fixed sequence of one- or two-week implementation PRs. The scope is too large, several dependencies are out of order, and a small number of payment, security, video, and rollback assumptions must be corrected before implementation.

The recommended engineering decision is:

Conditional go: proceed with foundations, repository validation, and technical spikes. Approve feature implementation only after the P0 findings are resolved, the financial and compliance contracts are signed off, and the plan is re-estimated using the actual repository state.
