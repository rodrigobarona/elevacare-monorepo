# Eleva.care v3 Identity And RBAC Spec

Status: Authoritative

## Purpose

This document defines the identity, tenancy, and authorization model for Eleva.care v3
(ADR-017, ADR-021). It replaces the prior identity-provider version of this file.

It should guide:

- Better Auth server, plugins and schema
- account lifecycle design
- organization and membership modeling
- RBAC implementation (`packages/auth/src/permissions.ts`)
- route and API authorization rules

## Identity Principles

- One human maps to one canonical Eleva user identity.
- Authorization is capability-based, not hardcoded to page names.
- Organizations and memberships are explicit.
- Guest access is a transitional state, not a separate identity system.
- RBAC is enforced at multiple layers, not only in the UI.
- Identity data lives in the main Neon project (`auth` schema) under the same DPA as
  domain data. Better Auth is self-hosted — it is not a new subprocessor.

## Identity Provider

**Self-hosted Better Auth** (ADR-017) is the locked identity, session, organization and
API-key provider. It is mounted in `apps/api` at `api.eleva.care/auth/*`
(`basePath: "/auth"`). Frontends never instantiate the server.

Better Auth is responsible for:

- authentication (e-mail OTP / magic link, Google OAuth, passkeys, TOTP)
- session cookies on `.eleva.care`
- organization and membership primitives
- role statements via `createAccessControl` (ADR-021)
- API keys and JWTs for agents
- encryption of OAuth tokens on `account` rows

Eleva remains responsible for:

- application-specific user profile data
- expert / member / org lifecycle state
- domain-specific authorization checks
- data ownership and visibility rules (Neon RLS, ADR-003)

Neon _managed_ Better Auth is rejected (Beta, partial `organization` plugin, no MFA, no
hooks). WorkOS AuthKit, Organizations, RBAC, Vault, Pipes and Widgets are removed (removed, see ADR-017).

## Core Identity Model

### User

One human. Tables: `auth.user` plus `main.users` (profile, locale, avatar URL on the DB
row — never the OAuth profile picture).

Examples: member, expert, organization admin, Eleva operator.

### Organization

The tenant boundary. `auth.organization` with `additionalFields.type` in
`personal | expert | team | academy | staff`. Personal orgs are **Spaces**
(`{firstName}'s Space`).

### Membership

`auth.member` — role (`owner | admin | member`), status, timestamps. Product label is
derived from `(organization.type, member.role)` (ADR-021), never stored as a third role
slug.

## Better Auth tables

Generated by the Better Auth CLI into `packages/db/src/schema/auth/*`, PostgreSQL schema
`auth`. Hand edits are limited to indexes, RLS class headers and `additionalFields`.

| Table          | Role                                            |
| -------------- | ----------------------------------------------- |
| `user`         | canonical identity                              |
| `session`      | cookie sessions; Redis `secondaryStorage` cache |
| `account`      | OAuth + credential accounts; tokens encrypted   |
| `verification` | magic-link / e-mail OTP tokens                  |
| `organization` | tenant; `type` additional field                 |
| `member`       | user ↔ org + seniority role                     |
| `invitation`   | org invites                                     |
| `twoFactor`    | TOTP secrets                                    |
| `passkey`      | WebAuthn credentials                            |
| `apikey`       | agent / M2M keys                                |
| `jwks`         | JWT signing keys                                |

`databaseHooks.user.create.after` provisions the personal Space inside `withAudit`.
Org switch is `organization.setActive`.

## Session and cookies

- `advanced.crossSubDomainCookies = { enabled: true, domain: ".eleva.care" }`
- `__Secure-` prefixed, `HttpOnly`, `SameSite=Lax`
- `session.cookieCache` 5 min
- `trustedOrigins` is an explicit environment list (never `*`)
- Preview deployments call the staging API and never mint `.eleva.care` cookies
- `admin.eleva.care` uses a host-only `__Host-` cookie (Phase 12)
- Cookie tossing / CSRF / subdomain model is gate **D-13**, written in Phase 2

Consumers:

- `@eleva/auth/client` — `createAuthClient` + matching client plugins
- `@eleva/auth/server` — `getSession()` = `React.cache`'d fetch of `/auth/get-session`
  forwarding cookies
- `@eleva/auth/proxy` — `getSessionCookie()` optimistic check in each `proxy.ts`;
  authorization is always re-checked server-side

`apps/api` `requireApiAuth` accepts exactly one credential per request: session cookie
(with origin check), `Authorization: Bearer <jwt>`, or `x-api-key`. Mixing modes is a 400. Cross-mode rejection is tested.

## Role Strategy (Locked)

Two layers:

- **Better Auth org-seniority roles** (`owner`, `admin`, `member`) — seniority inside an
  org, not product labels.
- **Eleva permission statements** in `packages/auth/src/permissions.ts` — the capabilities
  that actually authorize.

The **Eleva product label** (member, expert, clinic admin, operator) is derived from
`(organization.type, member.role)` plus capability bundles in `capabilities.ts`.

### Role catalog

| Eleva product label        | Role               | Org type                                      | Provisioning              |
| -------------------------- | ------------------ | --------------------------------------------- | ------------------------- |
| **Member**                 | `owner`            | Personal Space (org-of-one, auto-provisioned) | `user.create.after`       |
| **Expert (solo)**          | `owner`            | Expert org                                    | Become-Partner approval   |
| **Expert (clinic member)** | `member`           | Team (clinic) org                             | clinic admin invites      |
| **Clinic admin**           | `owner` or `admin` | Team org                                      | founder or elevation      |
| **Eleva operator (staff)** | staff plugin role  | Single internal `staff` org                   | Eleva staff accounts only |

Notes:

- A single human can hold memberships across multiple orgs. Organization-switching UX
  makes the current context explicit.
- An expert is either solo (`owner` of an expert org) or a clinic member — never both as
  the active context.
- Eleva platform staff are never `owner` of a customer's org. They operate from the
  `staff` org with the `admin` plugin roles
  `user | staff_support | staff_finance | platform_admin`.

### Permission bundles (examples)

Defined in `permissions.ts`, exposed as named bundles in `capabilities.ts`:

- `member_capabilities`: `bookings:view_own`, `sessions:view_own`, `billing:view_own`
- `expert_capabilities`: `schedule:manage`, `bookings:manage_own`, `reports:manage_own`
- `team_admin_capabilities`: expert + `members:manage`, `billing:manage_org`
- `staff_capabilities`: `admin.experts:approve`, `admin.payouts:approve`,
  `admin.audit:view_all`, …

The capability bundle drives access. Org seniority is the backbone it hangs on.

## Required Enforcement Layers

Every mutation (API route or Server Action) must authenticate and authorize
server-side. `proxy.ts` and layouts are not sufficient.

1. request / `proxy.ts` (optimistic cookie only — never the authorization decision)
2. page / layout (UX redirect)
3. Server Action / API handler — **mandatory**: `requireApiAuth` + capability check
4. data access (`withOrgContext` + RLS)

The UI is never the only protection. Unauthenticated mutations are forbidden.

## Account Lifecycles

### Member lifecycle

guest booking → provisional user (`emailVerified = false`) → activation magic link →
full dashboard.

### Expert lifecycle

application started → profile incomplete → review pending → approved → payout-ready →
published.

### Organization lifecycle

created → configured → billing ready → member-enabled → operational.

## Guest User Model

First-time bookings may create a user without a full account. The backend still preserves
a clean path: guest interaction → activation → full member identity. Guest status is an
onboarding state, not a separate actor type. Historical bookings attach on activation of
the same user id (not by e-mail match — ADR-019).

## Organization Context

The application resolves a current organization (Better Auth `session.activeOrganizationId`).
A user may belong to multiple organizations and be an expert in one context and a member
in another.

## Sensitive Data Access

Higher-risk permissions (transcripts, diary, documents, payouts, exports, membership
changes) are always audited via `withAudit()`. Clinical access is D-11 (author; clinic
opt-in; staff metadata-only). Break-glass decrypt is dual-control (Phase 12).

## Admin Versus Operator

Staff roles are not equal. `staff_support` ≠ `staff_finance` ≠ `platform_admin`.
High-trust actions (large refunds, payout release, partner approve, break-glass) require
step-up and dual control (Phase 12).

## Future Academy Compatibility

Reuse the same user and organization/membership concepts. Add academy-specific
permissions and profile extensions when Phase 16 promotes Academy.

## Audit Requirements

Log: sign-in/out where appropriate, membership changes, permission changes, organization
switches when security-sensitive, access to sensitive member data, expert approval and
status changes. Every mutating domain write uses `withAudit()`.

## Usernames And Public Slugs (Locked — ADR-014)

Public surface is username-first on `eleva.care/[handle]`. Governance lives in
`public_handles` (Phase 4 PR 04.1) — a shared unique namespace for experts and clinics,
backfilled from `expert_profiles.username`.

### Format rules

- 3–30 characters
- lowercase `[a-z0-9-]` only
- no leading or trailing hyphen
- no consecutive hyphens
- case-insensitive uniqueness

### Reserved path list

Maintained in `@eleva/config` `reserved-usernames.ts` and enforced at signup, a DB CHECK,
and admin tooling. Reserved set covers every first-segment path the gateway owns:

- authenticated: `patient`, `expert`, `org`, `admin`, `settings`, `callback`, `logout`
- zone prefixes: `docs`
- locale codes: `pt`, `es`, `en` (`br` stays reserved so `/br` cannot be captured; `pt-BR`
  URLs 301 to `/pt/*` per D-01)
- marketing + marketplace, help, auth + system, infra, future (`academy`, `courses`,
  `teams`), branded (`www`, `mail`, `status`, `sessions`, `email`)

`app` and `api` are not reserved (ADR-014). Adding a first-segment path requires adding
the slug to the reserved list **before** the route ships.

### Event-type slugs

Case-insensitive unique per expert. Booking URL:

- `eleva.care/[handle]/[event-slug]`
- `eleva.care/pt/[handle]/[event-slug]`
- `eleva.care/es/[handle]/[event-slug]`

## Tenancy Enforcement — Neon RLS

Identity + RBAC is one layer. The non-bypassable layer is Neon RLS (ADR-003).

- `withOrgContext(orgId, fn)` sets `SET LOCAL eleva.org_id`
- Every tenant table has an RLS policy class (see `schema-and-migration-rules.md`)
- Two Neon projects: `eleva_v3_main` + `eleva_v3_audit`
- Isolation test: insert as org A, select as org B → zero rows

## Encryption (ADR-020)

`@eleva/encryption` is envelope AES-256-GCM (per-org DEK wrapped by `ELEVA_KEK_V*`).
OAuth tokens are **not** in this package — Better Auth `account.encryptOAuthTokens`
covers Google/Microsoft. WorkOS Vault is removed (removed, see ADR-017).

CI rule: no `process.env.ENCRYPTION_KEY`, no `crypto.createCipheriv` outside
`packages/encryption` (and Better Auth's own internals).

## Guest Activation Flow

- Member books for the first time → Eleva creates a user with `emailVerified = false`
  tied to the booking
- Activation magic link sent post-booking
- Once activated, historical bookings already point at that user id
- Audit rows capture guest creation + activation

## Agent auth

Agents and M2M use `x-api-key` or `Authorization: Bearer <jwt>` issued by Better Auth.
They skip BotID (allow-list). Session cookies and JWTs are distinct schemes; a JWT in the
cookie slot or a session token as Bearer is rejected.

## Closed Decisions

- Better Auth is the identity provider (ADR-017). WorkOS (removed, see ADR-017).
- Role backbone = `owner` / `admin` / `member`; product labels from `(org_type, role)`
  (ADR-021)
- Organization-per-user default for solo experts and members
- Eleva operators live in a `staff` org with the admin plugin
- Neon RLS is the non-bypassable tenancy layer (ADR-003)
- Calendar OAuth tokens live in Better Auth `account` rows (ADR-017 amends ADR-004)
- Envelope encryption without a vault product (ADR-020)

## Open Questions

- Organization-switching UX polish when a user has many memberships (Phase 2 / account)
- Exact staff capability catalog (Phase 12)
